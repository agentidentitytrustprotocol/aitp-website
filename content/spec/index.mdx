This directory contains the normative RFCs that define the Agent Identity & Trust Protocol (AITP). AITP is an **agent-to-agent (A2A)** trust protocol; the current revision is **`aitp/0.3`** (v0.1 was the first published version; the v0.2 line re-serialized the portable trust artifacts as compact JWS and added cryptographic agility; `aitp/0.3` makes the envelope signature cover the whole envelope — see [RFC-AITP-0001 §1](/spec/core#1-status-of-this-memo)).

Status values below are drawn from the single lifecycle ladder in
[`governance/RFC-PROCESS.md`](https://github.com/agentidentitytrustprotocol/agentidentitytrustprotocol/blob/main/governance/RFC-PROCESS.md) — see that
document for what each stage means; `(opt-in)` is not a lifecycle stage,
it flags that the RFC is outside v0.3 core conformance (see below).

## Reading order

The numbering matches dependency order. Read top-to-bottom:

1. **[RFC-AITP-0001 Core](/spec/core)** — envelope, replay protection, signatures, error codes.
2. **[RFC-AITP-0002 Identity](/spec/identity)** — identity binding model and trust anchors.
3. **[RFC-AITP-0003 Manifest](/spec/manifest)** — signed agent self-description.
4. **[RFC-AITP-0004 Mutual Handshake](/spec/mutual-handshake)** — the four-message A2A handshake.
5. **[RFC-AITP-0005 TCT](/spec/tct)** — the canonical peer-issued Trust Context Token.
6. **[RFC-AITP-0006 Delegation](/spec/delegation)** — single-hop delegation between peers.
7. **[RFC-AITP-0007 Key Resolution](/spec/key-resolution)** — Manifest-first peer-key resolution and identity-issuer key resolution.
8. **[RFC-AITP-0008 Revocation](/spec/revocation)** — JTI deny lists per issuing peer, key revocation.
9. **[RFC-AITP-0009 Security](/spec/security)** — threat model and required defenses.

Opt-in (Draft normative text published, NOT part of v0.3 core conformance):

- **[RFC-AITP-0010 Session Trust Bundle](/spec/session-trust-bundle)** — multi-agent session scaling.
- **[RFC-AITP-0011 Multi-hop Delegation](/spec/multihop-delegation)** — chains beyond a single hop.

Reserved (a real, detailed document exists, but its contents are non-normative for `aitp/0.3` — see `governance/RFC-PROCESS.md`'s lifecycle for the Reserved/Planned distinction):

- **[RFC-AITP-0012 Extensions](/spec/extensions)** — ZK and TEE namespaces.

Planned (a materially thinner stub exists, reserving the number and giving other documents a stable link):

- **[RFC-AITP-0013 TCT Renewal Extension](/spec/tct-renewal-extension)** —
  standardization of the shortened renewal endpoint described
  non-normatively in
  [RFC-AITP-0004 §8.1](/spec/mutual-handshake#81-non-normative-shortened-renewal-extension).

## RFC lifecycle

`Reserved → Planned → Idea → Draft → Review → Release Candidate → Final Comment Period → Accepted` (or `Rejected`) — see [governance/RFC-PROCESS.md](https://github.com/agentidentitytrustprotocol/agentidentitytrustprotocol/blob/main/governance/RFC-PROCESS.md) for what a numbered RFC's `**Status:**` header reads at each stage; `scripts/check-doc-coherence.sh` asserts every one of the 13 RFC files (plus the repo `README.md`) draws from this ladder.

The `aitp/0.2` revision was a breaking change (compact-JWS trust artifacts, cryptographic agility), so RFCs 0001–0009 returned to **Draft** (shown simply as "Draft" above — the RFC's own `Version:` header, not its `Status:`, is what records which protocol revision a Draft belongs to) and re-progressed through the lifecycle; the v0.1 line completed Release Candidate at `0.1.0-rc.3`. The `aitp/0.3` revision (envelope signing input, issue #87) is breaking again, so every RFC stays at its current `Status:`.

The `aitp/0.3` revision reset every document's `Version:` header to `0.3.0`: RFC-AITP-0002, RFC-AITP-0003, RFC-AITP-0004, RFC-AITP-0005, RFC-AITP-0007 and RFC-AITP-0010 are at `0.3.0-draft`; RFC-AITP-0012 is at `0.3.0-reserved`; and RFC-AITP-0013 is at `0.3.0-planned`. RFC-AITP-0001 and RFC-AITP-0009 have since moved to `0.3.1-draft` (signature-string malleability documented), and RFC-AITP-0006, RFC-AITP-0008 and RFC-AITP-0011 to `0.3.1-draft` (a discarded revocation snapshot falls back to `revocation_policy.mode`). Within a revision, document versions may diverge again as each RFC takes its own editorial bumps; the minor position stays reserved for the protocol revision (see [`VERSIONING.md`](https://github.com/agentidentitytrustprotocol/agentidentitytrustprotocol/blob/main/VERSIONING.md)). The per-document history of the v0.2 line (where versions had diverged up to `0.2.14-draft`) is recorded in [`CHANGELOG.md`](https://github.com/agentidentitytrustprotocol/agentidentitytrustprotocol/blob/main/CHANGELOG.md) and in the frozen v0.2 line at commit `f9ee7ea` (tag `v0.2.1-draft`). Check the header of the document you are reading rather than assuming a shared version.

**Release Candidate** is the editorial stage after Review and before FCP: the RFC text is substantively complete, the version carries an `rc.N` suffix (e.g. `0.3.0-rc.1`; the v0.1 line reached `0.1.0-rc.3`), and further changes are limited to clarifications, KAT vectors, and conformance fixtures. RC can iterate (rc.1, rc.2, …) as implementer feedback surfaces issues. Promotion to FCP requires all required KAT vectors present, the conformance fixture set complete for the RFC's normative surfaces, and at least one implementation passing the core conformance tier. See [governance/RFC-PROCESS.md](https://github.com/agentidentitytrustprotocol/agentidentitytrustprotocol/blob/main/governance/RFC-PROCESS.md) for the full stage definitions.
